# 安全自检清单（部署前 / 变更后）

不是「跑一次就完事」的文档，而是**每次改动安全相关代码后照着走一遍**的清单。
每条都写清「怎么测、期望什么」，因为「以为配上了其实没生效」是这类功能最常见的失效方式。

> 本项目已有的对应实现见 [security.md](security.md)；本文只讲**怎么验证**。

---

## 一、部署前必测（约 10 分钟）

| # | 检查项 | 怎么测 | 期望结果 |
|---|---|---|---|
| 1 | 默认口令已改 | 用 `admin/admin123` 登录 | **失败**；自己新设的密码能进 |
| 2 | 权限确实拦得住 | 建一个只有「设备只读」的账号，访问 `POST /api/v1/admin/push` | `403` + `PERMISSION_DENIED`（**不能**返回 200 或静默成功） |
| 3 | 未登录访问管理端 | 无令牌请求 `GET /api/v1/admin/devices` | `401` + `AUTH_INVALID` |
| 4 | 教室端令牌不能越权 | 用 A 设备的 `HubDevice` 令牌回报 B 设备的指令 | 失败（设备身份与指令归属必须匹配） |
| 5 | 来源限制真生效 | 若配了 `ControlHub:AdminIpAllowList`：从**不在名单内**的机器访问管理端 | `403` + `IP_NOT_ALLOWED`；同时公开接口（`/api/v1/server/info`）仍 `200` |
| 6 | 来源限制没误伤自己 | 从名单内机器 + 本机（回环）访问管理端 | 正常进入（回环**永远**放行，否则桌面外壳会失效） |
| 7 | 安全响应头在位 | `curl -I http://服务器:29800/` | 有 `Content-Security-Policy`、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy` |
| 8 | 追踪 ID 贯通 | 同一个请求看响应头 `X-Request-Id` 与服务端日志里的 `traceId` | 两端一致 |
| 9 | 登录失败锁定 | 故意连错 5 次密码，再用**正确**密码 | `429` + `ACCOUNT_LOCKED`（不是继续放行） |
| 10 | 截图可控可查 | 教室端关掉「远程协助与隐私」，再从管理端下发抓屏 | 明确被拒并说明原因；管理端命令历史能看到该原因 |

## 二、改动安全相关代码后必测

改了**中间件 / 鉴权 / 权限 / 来源限制 / 加密 / 备份**后，除了上面 10 条，再补这几条：

| # | 检查项 | 为什么 |
|---|---|---|
| 11 | 白名单**正反两向**都测 | 只测「拦住」不够：地址族比较写错时会「谁都不拦」，只测「放行」也看不出问题。**必须**各测一次放行与拦截 |
| 12 | 老库升级后仍能启动 | 数据目录指向一份旧版数据库，启动一次 | 补列逻辑必须无损；不能出现「表已存在但缺列」导致启动失败 |
| 13 | 关闭开关后行为回到从前 | 例如 `SecurityHeadersEnabled=false` 后界面仍可用 | 逃生开关必须真的有效，且**在界面上看不出副作用** |
| 14 | 权限变更后旧账号的表现 | 新增权限键后，用老账号登录 | 要么按模板补上，要么明确报权限不足——不能「看似有权限但用不了」 |
| 15 | 前端不再用直链取受保护内容 | 全局搜 `href: '/api/v1` | 管理端受保护资源**必须**走带鉴权的取回方式（浏览器直链不带令牌，必然 401） |
| 16 | 加密相关改动跑回归并核对库底 | `dotnet test tests/ControlHub.Tests` 后，再直读 `hub.db` 确认 `code` / `secret` 为 `enc:v1:…` | 单测覆盖往返 / 幂等 / 明文兼容 / 换密钥必须失败 / 老库迁移 / 引用删除；**只看接口返回值看不出「说加密了其实没加密」** |

## 三、出问题时的定位顺序

1. **看响应码与错误码**：`401` → 凭证；`403` → 权限或来源；`429` → 锁定；
2. **拿 `X-Request-Id` 去搜日志**：能看到那次请求的完整处理与耗时；
3. **看审计日志**：`admin.login.failed` / `admin.login.locked` / `device.command` 等条目会写清「谁在什么时候做了什么」；
4. **看启动日志的安全开关回显**：来源限制、响应头、HTTPS 跳转、访问日志是否按预期开启——这类配置最怕「以为配了」。

## 四、已知未覆盖（别误判为已解决）

- **加密密钥 `secrets.key` 与数据库同机**：注册码 / 邀请码 / Webhook 密钥已是密文存储（#36），
  但密钥文件与 `hub.db` 放在一起——同时拿到两者则加密没有额外保护。密钥文件**不得随备份外发**，
  换机器时数据库与密钥要一起搬（见 `docs/security.md` 第六节、`docs/deployment.md`）。
- **只有管理端关键操作的审计日志**，没有逐请求的访问日志表（访问日志走的是服务端日志文件）。
- **设备令牌是对称令牌**：被完整复制即可冒充该设备。发现异常时停用设备并重新注册。
- **没有自动漏洞扫描**（Dependabot 只做依赖版本提醒，不做代码扫描）。

上面几条在 [roadmap.md](roadmap.md) 的有序待办里；在那之前，请用网络层手段（防火墙、反代来源限制、VPN）补足。
