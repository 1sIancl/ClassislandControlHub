# ADR-0003：先冻结插件扩展协议，再写实现

- 状态：已接受（协议草案见 [plugin-protocol.md](../plugin-protocol.md)）
- 日期：2026-10-02
- 相关：[ADR-0002](0002-permission-model.md)

## 背景

路线图里「插件扩展机制」是项目从**工具**走向**平台**的关键：让其它 ClassIsland 插件把自己的能力接进集控，
由集控统一下发、统一查看。第三方接入意味着**协议一旦发布就要长期兼容**——外部插件作者会照着它写代码，
改协议的代价由别人承担。

同时项目已经有一套内部命令协议（`shell` / `plugin.*` / `appearance.*` / `notify` / `power.*` /
`automation.*` / `diagnostic.*`），如果直接把它当扩展协议开放，等于把「内部随便改的自由」一起开放出去。

## 决策

**先冻结一份最小、可版本化、可增量演进的扩展协议文档，再实现。**

具体冻结内容（详见 plugin-protocol.md）：

1. **操作类型 ID 命名空间**：内置保持现状；扩展**必须**用 `ext.<插件ID>.<操作名>`；
   `ext.local.*` 保留给集控自身；**不认识的 `ext.*` 一律拒绝**（fail-closed，与 ADR-0002 一致）。
2. **能力声明**：随插件清单上报 `capabilities`（`id` / `title` / `pluginId` / `permission` /
   `idempotent` / `maxDurationSeconds` / `parameters` / `result`）——**作为可选字段**，旧插件不报也能正常工作。
3. **参数 Schema**：只支持受限子集（string / number / integer / boolean / enum + `x-ui` 提示），
   **不支持数组与嵌套对象**——因为 A 端要能可靠地自动生成表单，Schema 越自由，自动生成越容易出错。
4. **权限声明**：每个能力必须声明 `remote.read` / `remote.write`，预留 `ext.<插件ID>` 细粒度命名空间。
5. **回报与生命周期**：一次性派发、2 小时 TTL、`maxDurationSeconds` 仅作提示**不强制中断**、
   v1 **不自动重试**（避免第三方能力被重复执行造成副作用）。
6. **错误码**：`EXT_UNSUPPORTED` / `EXT_INVALID_PAYLOAD` / `EXT_DENIED` / `EXT_TIMEOUT` / `EXT_INTERNAL`。
7. **兼容矩阵**：明确「旧插件 + 新 A 端」「新插件 + 旧 A 端」「未知字段」三种落差各自的行为，
   并定义**最小可用能力集**（注册 / 心跳 / 对时 / 下发 / 回报）。

## 理由

- 协议是**外部依赖**：发布后改名、改语义都会破坏别人的插件，属于「一次性成本换长期稳定」的典型场景。
- 先冻结再实现，可以避免实现过程中被具体代码结构带偏——文档逼着我们回答「参数怎么描述」「权限怎么声明」
  这类一旦发布就很难改的问题。
- 把「不认识的 `ext.*` 拒绝」写进协议，是为了让**新旧两端版本错配时行为可预期**：明确报错，
  而不是静默忽略或半执行。

## 代价

- 扩展能力暂时**不能表达复杂参数**（数组、嵌套对象），复杂能力需要先用内置命令或简化为多个单值参数。
- v1 不提供：在 A 端执行插件代码、插件自绘 UI、自动重试、跨设备编排（都写进了「v1 不做」清单）。

## 后续

按 plugin-protocol.md 的落地顺序实现：能力上报 → 下发前校验（拒绝未知 `ext.*`）→ A 端自动表单 →
真实第三方插件接入验证。**实现期间若发现协议需要改动，先改文档再改代码。**
