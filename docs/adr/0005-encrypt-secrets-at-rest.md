# ADR 0005：静态敏感数据加密（注册码 / Webhook 加签密钥）

- 状态：**已决定，待实现**（路线图 `#36`，安全清单里最后一条已知限制）
- 日期：2026-10-03
- 相关：`docs/security.md`、`docs/pentest-checklist.md`、ADR 0001（SQLite + 轮询）

## 背景

以下数据目前**明文**存在 `data/hub.db`：

| 表 / 列 | 内容 | 泄露后果 |
|---|---|---|
| `enroll_codes.code` | 注册邀请码（一次性/多次） | 拿到即可把自己的机器注册进集控 |
| `webhooks.secret` | 钉钉加签密钥 | 可伪造推送到群机器人 |
| `backup` 文件（若有） | 上述内容的副本 | 同上 |

管理员密码是哈希（不可逆）✓、开放 API 密钥只存哈希 ✓——这两类**不在本 ADR 范围内**。
威胁场景明确为：**管理端服务器磁盘 / 数据库文件 / 备份文件被拷走**（U 盘、误传、云盘同步、离职带走）。
不防"服务器被完全控制"（那时密钥文件同样可读），也不防内存取证。

## 决策

### 1. 加密算法与封装格式

- **AES-256-GCM**（`System.Security.Cryptography.AesGcm`），每次写入用随机 12 字节 nonce，认证标签 16 字节。
- 存储格式统一为文本，便于放进现有 `TEXT` 列并肉眼辨认：

  ```
  enc:v1:<base64(nonce)>:<base64(ciphertext)>:<base64(tag)>
  ```

- **未加密的历史值保持原样**（不带 `enc:` 前缀）——读取时按前缀判断，因此**老库无需停机迁移**。

### 2. 密钥管理

- 密钥文件：`data/secrets.key`（32 字节随机，Base64 存储，权限尽量收紧为仅服务账号可读）。
- **首次启动自动生成**；已存在则加载。密钥文件与数据库**不要放在同一个会被整体拷走的目录**的假设下——
  这是本方案的天花板：**若攻击者同时拿到 `.db` 与 `.key`，加密不提供额外保护**。
  因此同时在 `docs/security.md` 写明：**把 `secrets.key` 纳入"不得随备份一起外发"的清单**（可选：部署时用
  `ControlHub:SecretsKeyPath` 指向数据库目录之外的位置，例如宿主机受控目录）。
- 支持通过配置项 `ControlHub:SecretsKeyPath` 指定路径；不配则落在 `data/secrets.key`。

### 3. 写入即加密，读取兼容明文

- **写入路径**（生成注册码、保存 Webhook）→ 一律写密文。
- **读取路径** → 有 `enc:v1:` 前缀则解密，否则按明文返回（兼容老数据）。
- 启动时执行一次**幂等迁移**：把仍是明文的 `enroll_codes.code`、`webhooks.secret` 就地加密
  （`UPDATE ... WHERE 列 NOT LIKE 'enc:v1:%'`），失败只记日志、不阻断启动。
- 解密失败的**单条记录**：按"该值不可用"处理（注册码视为失效、Webhook 视为未配置密钥），
  并在管理端「服务器信息」里给出计数告警——**不静默降级为明文**。

### 4. 可观测性（便于核对"到底加密了没有"）

- `/api/v1/admin/server/info` 增加 `secretsEncrypted` 字段：
  `{ enrollCodes: { total, encrypted }, webhooks: { total, encrypted }, keyFile: "data/secrets.key" }`。
- 启动日志打印一行：`静态敏感数据：注册码 x/y 已加密，Webhook 密钥 m/n 已加密（密钥文件 …）`。

### 5. 密钥轮换（留接口，不实现自动轮换）

- 提供一次性命令：以 `secrets.key` 为输入，把带 `enc:v1:` 的值全部解密再用新密钥重加密。
- 自动轮换**不做**：轮换期间需要同时接受新旧密钥，复杂度与收益不匹配单机部署场景。

## 后果

**好处**

- 拷走 `hub.db`（或它的备份）不再等于拿到可用的注册码与群机器人密钥。
- 老库零停机、零手工步骤；一条一次性迁移在启动时完成。
- 有可核对的计数，不会出现"以为加密了其实没有"（这正是本项目里反复踩过的坑）。

**代价与风险**

- **多一个必须保管好的文件**（`secrets.key`）：丢了 = 注册码与 Webhook 密钥不可恢复（需要重新生成/重配）；
  因此密钥文件**不放进**自动备份包，且在 `docs/troubleshooting.md` 写明处置办法。
- 数据库不再"自包含"：迁移机器时必须**同时**搬运 `.key`，这一点要写进部署文档，否则表现为
  "Webhook 全部报密钥无效、注册码全部失效"。
- 备份加密（`#63`）与此互补但不同：本 ADR 只解决"落库的值"，备份整包加密另做。

## 实现期修正：注册码是主键，不能直接加密（2026-10-03）

读表结构时发现一个**会直接把注册功能搞坏**的问题：`enroll_codes` 的 **`code` 就是主键**，
而 AES-GCM 是**随机化加密**——同一个注册码每次加密结果都不同，因此**无法再用 `WHERE code = ?` 查找**。
若照原方案直接加密主键，表现是「所有注册码都查不到」＝教室端再也注册不上。

修正后的做法：

1. **新增列 `code_hash TEXT`**：`HMAC-SHA256(secrets.key, 规范化后的注册码)` 的 Base64。
   它是**确定性**的，可以建唯一索引并用于精确查找。不用裸 SHA-256 的原因：注册码通常只有 8 位左右，
   裸哈希可被离线爆破；加 HMAC 后，**只拿到 `hub.db` 也推不出注册码**。
2. `code` 列改为存**密文**，只用于管理端**列表展示**（需要时解密）。
3. 校验流程改为：规范化输入（大写、去空格）→ 算 HMAC → 按 `code_hash` 查行 → 校验有效期与剩余次数
   → （仅展示时才解密 `code`）。
4. **迁移顺序不可颠倒**：先为老行补算 `code_hash`（此时 `code` 还是明文，可直接算），再加密 `code`。
5. 主键值保持原样（老库明文、新库密文）——主键只作行标识，不参与查找语义；
   若将来要彻底消除主键明文，另起一次迁移改为主键用行 ID。

`webhooks.secret` 不参与任何查找，按原方案直接加密即可，无此问题。

## 落地顺序（实现时按此执行，每步都可独立验证）

1. `SecretProtector`（加解密 + `enc:v1:` 封装 + 密钥加载/生成），单元测试覆盖：往返、错误密钥、篡改标签、明文兼容。
2. 接入写路径：注册码生成、Webhook 创建/更新。
3. 接入读路径：注册码校验、Webhook 发送前取密钥。
4. 启动迁移：明文 → 密文（幂等；日志报告条数）。
5. 诊断输出：`server/info` 计数 + 启动日志 + 管理端展示。
6. 文档：`security.md`（密钥文件保管清单）、`deployment.md`（迁移机器必须带 `.key`）、`troubleshooting.md`（密钥丢失表现与处置）。
7. 端到端实测（必须）：创建注册码 + 配 Webhook → 直接读数据库确认是密文 → **用明文形态手工塞一条老数据** →
   验证仍能正常使用 → 重启后迁移把它变成密文 → 停服删掉 `.key` → 验证表现为"注册码失效 + Webhook 提示密钥无效"而不是崩溃。
