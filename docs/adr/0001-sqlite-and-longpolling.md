# ADR-0001：用 SQLite + 长轮询，而不是「数据库服务器 + 消息推送」

- 状态：已接受
- 日期：2026-09（回填记录）
- 相关：[README「规模与部署建议」](../../README.md)、[ADR-0004](0004-render-pipeline-screenshot.md)

## 背景

目标用户是**学校信息中心 / 电教委员**，不是有专职运维的互联网公司。部署方通常只有一台校内服务器（甚至是一台
PC 改的机器），没有 DBA、没有消息队列、也未必有容器平台。而使用规模可能从 20 间教室到 800+ 间教室。

要在这个约束下同时满足：**装得起来、跑得住、出了问题能自己查**。

## 决策

1. **存储用 SQLite**（WAL 日志模式、`busy_timeout`、连接池），数据目录是单个文件。
2. **教室端不使用消息推送，改用长轮询**：客户端 `GET /client/wait` 挂起最多 60 秒；服务端所有等待者挂在
   **同一个共享变更信号**上，信号触发后各自做 2 次轻量查询判断自己是否需要同步；心跳默认 30 秒兜底。
3. **不做外部依赖**：不要求 Redis / RabbitMQ / 独立数据库。

## 理由

- **SQLite 的运维成本接近于零**：备份 = 复制文件（本项目还提供一键备份与恢复），迁移 = 换机器拷目录，
  排错 = 拿任意 SQLite 工具打开看。换成 PostgreSQL 立刻引入「要装服务、要建库、要管账号密码」的门槛。
- **长轮询在这个规模下够用且更好诊断**：空闲时一台设备只占 1 个挂起的异步请求，**不占线程、不做轮询**；
  相比 WebSocket 少一层连接状态管理，反代/NAT 也更友好（这也是为什么 README 明确要求反代放行长连接）。
- **写压力可控**：心跳是单条 UPDATE，亚毫秒级；按 800 台估算是 ~27 次写/秒，SQLite 单机完全吃得下。
  真正的瓶颈通常在**学校上行带宽与教室网络**，而不是服务端 CPU。

## 代价与已知限制

- **单机写串行**：极端写密集场景会成为瓶颈（本项目没有这种场景）。
- **删除不收缩文件**：需要真正缩小体积时要停服 `VACUUM`（已在排查指南中写明）。
- **数据库不能放网络盘 / 同步盘**：会因文件锁出现 `database is locked`（已写进部署建议）。
- **没有多实例共享**：>800 台建议分校区多实例部署，而不是横向扩同一份数据。
- **长轮询的规模上限**：`WaitSeconds` 上限 60 秒意味着「变更到生效」最坏有秒级延迟，对本场景完全够用
  （课表与配置不需要毫秒级实时）。

## 何时应该推翻这个决策

出现下列任一情况，就应认真评估迁移到 PostgreSQL + 独立推送通道：

- 需要**双机热备 / 高可用**：单文件数据库无法安全共享给多实例；
- 设备规模到数千台且**心跳写成为瓶颈**（可先用调大 `OnlineTimeoutSeconds` 换来线性降低写频率，仍不够再迁移）；
- 需要**多租户 / 云端 SaaS**：届时租户隔离、备份与配额都会逼着换存储。
